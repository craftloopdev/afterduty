# Legacy Gap Analysis & Strategy/Scenarios Pipeline — Engineering Map

Baseline map of the EXISTING Spring pipeline (branch `feat/next-web-foundation`, June 2026) for the redesign as a dynamic Claude-agent workflow on Vertex AI. All paths relative to `spring-backend/src/main/java/com/afterduty/` unless noted.

**Headline architecture:** The classes named in older docs (`EnhancedGapAnalysisOrchestrator`, `StrategyOrchestrator`) are dead shells. The live pipeline is three hand-rolled, DB-backed state machines (`extraction` → `synthesis` → `gap`) driven by a 15-second polling scheduler, with all LLM calls funneled through a provider-agnostic async job queue (`LlmJob` table + submitter/poller workers) that routes per-purpose to either the **Anthropic Message Batches API (direct, claude-opus-4-7)** or **Vertex AI Gemini streaming (gemini-3.1-pro-preview)**.

- `service/gap/EnhancedGapAnalysisOrchestrator.java:7-12` — "Thin shell retained for Spring context compatibility. The active gap analysis pipeline is driven by GapStateMachine."
- `service/synthesis/StrategyOrchestrator.java:16-32` — `@Deprecated`; `runOptimizedSynthesis()` throws `UnsupportedOperationException`. (So `StrategyDebugController`'s POST endpoints 500 today — see Weaknesses.)

## 1. STAGES — ordered control flow

### 1.0 Trigger layer: `AnalysisScheduler` (service/AnalysisScheduler.java)

- `@Scheduled` `tick()` every `va-claim.pipeline.poll-ms` (default **15000 ms**, initial delay 20 s) — AnalysisScheduler.java:120-138. It does `claimRepository.findAll()` and tries to advance every claim.
- Per claim (`advanceClaim`, :140-160), gated **only** by `hasActiveSubscription` (:164-169):
  1. Extraction ticks if `claim.extractionState != null && != "COMPLETE"`.
  2. Synthesis ticks if `shouldRunSynthesis` (:173-194): in-flight state, OR (has atoms AND quiet ≥ `va-claim.pipeline.quiet-seconds` default 30 s AND no evidence rows in `pending/processing` AND (never synthesized OR configured model changed OR newest atom > `lastSynthesisAt`)).
  3. Gap ticks if `shouldRunGapAnalysis` (:198-214): in-flight state, OR (synthesis done at least once AND not in progress AND (never ran OR configured model changed OR `lastSynthesisAt > lastGapAnalysisAt`)). A TODO-ish branch at :210-213 notes `IdentifiedCondition` has no `updatedAt`, so hand-edited conditions can never re-trigger gap analysis.
- Completion callbacks `markSynthesisComplete` / `markGapAnalysisComplete` (:218-238) null the state, clear in-progress, stamp `lastSynthesisAt/Model` and `lastGapAnalysisAt/Model` on `Claim` (model/Claim.java:57-88 — `extraction_state`, `synthesis_state`, `gap_state`, `last_*` columns).
- Everything is **async/poll-driven**: nothing blocks on a model. There is no event/webhook; latency floor per state transition is one scheduler tick (15 s) + one LLM-poller tick (15 s).

### 1.1 Upstream synthesis state machine (`service/synthesis/SynthesisStateMachine.java`) — produces the `IdentifiedCondition` rows that gap analysis consumes

`Claim.synthesisState` string enum `NONE → IDENTIFYING → MERGING → RATING → VERIFYING → COMPLETE`; one transition max per tick (`advance`, :81-92).

| Transition | What happens | LLM purpose / fan-out |
|---|---|---|
| NONE → IDENTIFYING (`doIdentify` :98-114) | Loads all atoms; builds service + presumptive context via `EnhancedSynthesisOrchestrator.buildServiceContext/buildPresumptiveContext` (synthesis/EnhancedSynthesisOrchestrator.java:118-159, from `ServiceProfile` + `PresumptiveRulesService`); submits 1 job | `synthesis_identify` ×1 (Gemini) |
| IDENTIFYING → MERGING (`doMergeIfReady` :120-150) | When identify SUCCEEDED, parse condition list; if empty fast-path COMPLETE; else submit merge job | `synthesis_duplicate_merger` ×1 (Claude batch) |
| MERGING → RATING (`doRateIfReady` :156-197) | Re-parses identify result (via `pjobs.get(0)` — order-fragile, see Weaknesses), applies merger verdicts (`DuplicateConditionMerger.parseResponse`), **persists `IdentifiedCondition` rows** (`coordinator.mapToCondition` :179, EnhancedSynthesisOrchestrator.java:94-116), fans out 1 rating job per condition with **all claim atoms** | `synthesis_rate` ×N (Gemini) |
| RATING → VERIFYING (`doVerifyIfReady` :203-255) | Writes `estimatedRating/ratingRationale/confidence` per condition; submits 1 cross-condition verification job | `synthesis_verify` ×1 (Gemini) |
| VERIFYING → COMPLETE (`doCompleteIfReady` :261-305) | Parses issues, `coordinator.applyCorrections` (pyramiding / rating_mismatch / invalid_code flags, EnhancedSynthesisOrchestrator.java:55-91), saves `pyramidGroup/pyramidReason`, calls `markSynthesisComplete(claimId, modelName-of-verify-job)` | — |

### 1.2 Gap state machine (`service/gap/GapStateMachine.java`) — the "Gap analysis & scenarios" pipeline proper

`Claim.gapState` enum `NONE → EVIDENCE_GAPS → VALIDATING → WHATIF → COMPLETE` (:33), one transition per tick (`advance` :68-78).

1. **NONE → EVIDENCE_GAPS** (`doFanoutEvidence` :84-120). For each `IdentifiedCondition` of the claim: build a gap request via `EvidenceGapAnalyzer.buildRequest` with **all atoms of the claim** (:93-98), batchGroupKey `gap_evidence_{claimId}`, submit, and record a `ClaimPipelineJob(claimId, "gap_evidence", llmJobId, conditionId)`. No conditions → fast-path COMPLETE (:87-91). Sets `gapAnalysisInProgress=true`.
2. **EVIDENCE_GAPS → VALIDATING** (`doFanoutValidatingIfReady` :126-182). Gate: `llmJobService.allSucceeded(all gap_evidence jobIds)` (:131-132) — if **any** job is non-SUCCEEDED (including FAILED) it returns and waits forever. On pass: parse each result (`EvidenceGapAnalyzer.parseResponse`) and **persist gaps onto `IdentifiedCondition.gaps`** (:139-147). Then fan out one `gap_validation` job per condition that has gaps (proposed gaps serialized into the prompt, :149-169). No gaps anywhere → fast-path COMPLETE (:171-176).
3. **VALIDATING → WHATIF** (`doFanoutWhatIfIfReady` :188-249). Gate: all validation jobs SUCCEEDED (partial failure = stuck, :193-198). Applies adversarial verdicts via `GapValidationAgent.parseResponse` — keep/drop, priority override, revised text — and overwrites `condition.gaps` with the validated list (:203-214; merge logic GapValidationAgent.java:159-215). Fans out one `gap_whatif` job per condition with surviving gaps (:216-237); none survive → fast-path COMPLETE.
4. **WHATIF → COMPLETE** (`doCompleteIfReady` :255-280). Parses scenario arrays and persists to `IdentifiedCondition.whatIfScenarios` (:263-271). Takes `modelName` from the **first whatif job** (:274-276) and calls `analysisScheduler.markGapAnalysisComplete(claimId, modelName)`.

### 1.3 LLM job layer — submission, retries, failure handling

- `LlmJobService.submit` (service/llm/LlmJobService.java:51-81): persists a `QUEUED` `LlmJob` row with full serialized request payload; never blocks.
- `LlmJobSubmitter` (service/llm/LlmJobSubmitter.java): every 3 s (`va-claim.llm.submitter.poll-ms`, batch-size 50) pulls QUEUED rows with `SELECT … FOR UPDATE SKIP LOCKED`, groups by `(provider, batchGroupKey)`, one provider submit per group (:43-92). **Submit retry: 3 attempts then status FAILED** (:79-89).
- `LlmJobPoller` (service/llm/LlmJobPoller.java): every 15 s (`va-claim.llm.poller.poll-ms`) polls active provider jobs, persists results, writes an `AiCallLog` per terminal job (:127-165). **Orphan recovery**: SUBMITTED rows older than `va-claim.llm.orphan-deadline-min` (30 min) are reset to QUEUED (:113-125) — designed for JVM restarts losing the Gemini provider's in-memory state.
- Stage gates in both state machines use `allSucceeded` only; `allTerminal` (LlmJobService.java:106-109) exists but is never used by the gap/synthesis machines → **a single terminal-FAILED job permanently stalls the claim's pipeline** with no stage-level retry, no user-visible error, and `gapAnalysisInProgress` stuck true.
- Manual driver: `controller/GapAnalysisDebugController.java` — `POST /api/claim/debug/enhanced-gap-analysis` ticks `gapStateMachine.advance(claim)` once (:39-54); `GET /api/claim/debug/gap-detail/{conditionId}` dumps gaps + what-ifs (:59-76, no per-user scoping on the condition, but all `/api/claim/debug/**` is admin-gated by config/SecurityConfig.java:103-109).
- Legacy sync path still wired: `PipelineService.runFullPipeline/runSynthesisOnly/runGapAnalysisOnly` (service/PipelineService.java:159-224) → `ClaudeSynthesisService` (despite the name, calls **Gemini synchronously**, ClaudeSynthesisService.java:23,42-56) + `ConditionPostProcessService.postProcess`. Reached only from `IntakeController` debug endpoints (:459, :555, :577).

| `gap_validation` | Anthropic direct | claude-opus-4-7 | Batches | 8192 / 8000 (effort medium) |

Routing table: LlmProviderRouter.java:40-52. Defaults: LlmProviderRouter.java:89-95.

- **Anthropic provider** (`AnthropicBatchProviderImpl.java`): direct `api.anthropic.com/v1/messages/batches`, `x-api-key` = `va-claim.claude.api-key` (`ANTHROPIC_API_KEY`), `anthropic-version: 2023-06-01` (:42-49). One POST per batch group; poll on `processing_status`; results fetched as JSONL keyed by `custom_id`=job UUID (:145-199). `thinkingBudget>0` translates to `thinking: {type: adaptive}` + `output_config.effort` low/<4k, medium/<12k, high (:254-266). **Not Vertex — Anthropic is consumed directly.**
- **Vertex Gemini provider** (`VertexGeminiAsyncProviderImpl.java`): deliberately avoids the Vertex Batch Prediction API ("24h SLA and requires GCS bucket I/O — too slow", :23-27). Instead one **virtual thread per call** to `https://aiplatform.googleapis.com/v1/projects/{p}/locations/{loc}/publishers/google/models/{m}:streamGenerateContent?alt=sse` (:180-182), ADC credentials, `temperature` hard-coded **0.2** (:169), results buffered in an in-memory `ConcurrentHashMap` (:51) — lost on restart (recovered by 30-min orphan requeue).
- Config keys (resources/application.yml): `va-claim.claude.model: ${CLAUDE_MODEL:claude-opus-4-7}` (:57), `va-claim.gemini.model: ${GEMINI_MODEL:gemini-3.1-pro-preview}` (:54), `location: ${GCP_LOCATION:global}`, `va-claim.gcs.bucket: ${GCS_BUCKET:vaclaim-documents}` (:50 — used only for document storage, never for LLM I/O), submitter/poller cadences (:58-64). `va-claim.gemini.thinking-budget` is referenced in code with default 10240 but not present in any yml.

### Prompts & structured output

All prompts are **Java text blocks compiled into the service classes** — no template files, no versioning:

- `EvidenceGapAnalyzer.SYSTEM_PROMPT` (gap/EvidenceGapAnalyzer.java:37-84): VASRD-aware "evidence strategist"; hard rules (must cite 38 CFR Part 4 criterion verbatim, no duplicate evidence, presumptive ⇒ usually no nexus letter); fixed 13-item gap-type enum; JSON array schema with `type/title/description/vasrd_reference/current_rating/target_rating/triad_leg/priority/rating_impact/how_to_get_it/estimated_time/estimated_cost_usd`. User message includes condition header, `MasterlistService.contextForCondition` KB slice (KB match + ≤12 sibling VASRD codes from `resources/masterlist/conditions.json`, scraped from veteransbenefitskb.com — MasterlistService.java:14-28,157-190), triad summary, and the full atom dump grouped by type (:115-142).
- `GapValidationAgent.SYSTEM_PROMPT` (gap/GapValidationAgent.java:33-85): adversarial **RVSR rater persona**; REAL/CRITICAL/NEEDED test per gap; rater reality-check heuristics (presumption granted ⇒ nexus not real; buddy statements don't move orthopedic ratings; private opinions < VA exams; etc.); returns one JSON object `{validated_gaps:[{original_index, keep, is_real, is_critical, is_needed, rater_priority, rater_note, revised_description, revised_how_to_get_it}], overall_note}`. Verdicts merged onto original gaps in code (:159-215), `rater_overall_note` stashed on the first surviving gap (:205-207).
- `WhatIfScenarioGenerator.SYSTEM_PROMPT` (gap/WhatIfScenarioGenerator.java:34-49): "rating impact analyst"; per gap output `scenario/action/current_rating/potential_rating (valid set 0-100)/monthly_delta ("use 2024 VA rate tables" — stale)/action_required/confidence/timeline`, JSON array ordered by monthly_delta desc.
- Synthesis prompts: `ConditionIdentificationAgent.java:30-51` (identify + triad STRONG/MODERATE/WEAK/MISSING, secondary/bilateral/TDIU hints), `RatingAgent.java:35-63` (rating thresholds **hard-coded in the prompt** for asthma/PTSD/tinnitus/sleep apnea/GERD, plus VASRD criteria looked up from `resources/vasrd_codes.json` via `VasrdDataService`, and an inline pre-computed corticosteroid course count :153-185), `SynthesisVerificationAgent.java:28+`, `DuplicateConditionMerger.java:30+`.
- **Structured-output approach: none beyond prompt discipline.** Every agent strips markdown fences (`cleanJsonResponse`) and Jackson-parses into `List<Map<String,Object>>`. No tool-use/JSON-schema enforcement (`LlmJobRequest.tools` exists, :22, but is never set by these agents). Parse failures degrade silently: empty gap list (EvidenceGapAnalyzer.java:160-168), "keep originals" (GapValidationAgent.java:211-214), empty scenarios (WhatIfScenarioGenerator.java:110-118), default rating 0 confidence 0.3 (RatingAgent.java:122-130).

## 4. INCREMENTAL BEHAVIOR — new document after a completed analysis

Today it is a **full redo of all three phases, implemented append-only, with cross-run contamination**:

1. Upload → `PipelineService.processEvidence` (PipelineService.java:60-123): usage-cap check (deferred if at cap), evidence marked `processed/“Queued for async extraction”`, `claim.lastEvidenceAt=now`, `synthesisNeeded=true`, and `extractionState="NONE"` if currently null (it is null, because extraction completion nulls it — ExtractionStateMachine.java:219-226).
2. **Extraction re-runs over ALL evidence items, not just the new one**: each `startStage` iterates `evidenceItemRepository.findByClaimId(claim.getId())` (ExtractionStateMachine.java:120-141) and `saveAtoms` always inserts (:349+). Every re-run therefore re-extracts and **duplicates atoms for every previously processed document**. Worse, `advanceIfReady` gathers `findByClaimIdAndStage` which includes the SUCCEEDED `ClaimPipelineJob` rows of the *previous* run (never deleted), so `parseStageResults` re-parses old results and re-inserts their atoms again (:196-218). Only the events stage is incremental (`extracted=false` filter, :154).
3. Synthesis: scheduler sees newest atom > `lastSynthesisAt` (+30 s quiet, no in-flight extraction) → `shouldRunSynthesis` true (AnalysisScheduler.java:191-193) → the whole identify→merge→rate→verify chain re-runs **from scratch over all (now duplicated) atoms**. New `IdentifiedCondition` rows are appended (SynthesisStateMachine.java:177-181); **nothing deletes the previous run's conditions in the async path** (`deleteByClaimId` is only called from the admin debug endpoint, IntakeController.java:552; `ConditionPostProcessService.postProcess` dedup/supersede runs only in the legacy sync path, PipelineService.java:176 and IntakeController.java:591).
4. Gap analysis: `lastSynthesisAt > lastGapAnalysisAt` → full gap re-run across **all** conditions (old + new duplicates), again reading stale `gap_evidence`/`gap_validation` pipeline rows from prior runs in its readiness checks and parse loops (GapStateMachine.java:127-147, :189-214).
5. **Invalidation summary:** a new atom invalidates synthesis (timestamp comparison) which invalidates gap analysis (timestamp comparison). Nothing invalidates or deletes the *artifacts* themselves — gaps/scenarios are overwritten per condition-id, but superseded conditions from earlier runs keep their stale gaps and remain visible unless the sync dedup path is manually invoked.
6. **De facto perpetual re-run bug:** the "model changed" triggers compare `va-claim.claude.model` (`claude-opus-4-7`) to `lastSynthesisModel`/`lastGapAnalysisModel` (AnalysisScheduler.java:192, :207) — but the machines store the model of a *verify/whatif job*, which routes to Vertex and is therefore `"gemini-3.1-pro-preview"` (SynthesisStateMachine.java:297-303; GapStateMachine.java:273-278), or `"unknown"` on fast-paths. The strings can never match, so structurally `shouldRunSynthesis`/`shouldRunGapAnalysis` return true on every tick after completion → continuous re-analysis loops for any subscribed claim with atoms (compounded by the append-only behavior above). This should be verified against prod `ai_call_logs` before redesign assumptions are locked, but the code path is unambiguous.

## 5. COST — tracking and capping

- **Per-call ledger:** `LlmJobPoller.recordCost` builds an `AiCallLog` from job + token usage on every terminal job (LlmJobPoller.java:127-165); `AiCostService.computeCosts` prices it from a hard-coded per-1M table "as of April 2026" (AiCostService.java:22-32): gemini-3.1-pro-preview $2/$12/$12, gemini-2.5-pro $1.25/$10, gemini-2.5-flash $0.30/$2.50, claude-opus-4-7 and -4-6 $15/$75, claude-sonnet-4-6 $3/$15, claude-haiku-4-5 $0.80/$4; unknown model fallback $5/$15 (:64-65). **The 50% Anthropic Batches discount (noted in AnthropicBatchProviderImpl.java:25-26) is NOT applied — Claude batch spend is logged at 2× actual.** `cache_read/write_tokens` columns exist (AiCallLog.java:47-51) but are never populated; no prompt caching anywhere.
- **Alerts:** log-only daily thresholds — WARN > $5/day, ERROR > $20/day across all users (AiCostService.java:84-92).
- **Per-user cap:** `usage.limit-cents: 400` ($4/month, UTC calendar month) + `usage.enabled` + `USAGE_UNLIMITED_EMAILS` allowlist (application.yml:23-29); `UsageService.getCurrentUsage` sums `AiCallLog.totalCost` per user (UsageService.java:29-66 — note comment: cap applies to paid users too as fair-use ceiling on the $11.99/mo plan); `UsageGuard.assertCapacity` throws `UsageLimitException` (UsageGuard.java:18-24). **Enforced only at extraction entry (PipelineService.java:72, evidence becomes `deferred_usage_limit`) and chat (ChatService.java:71). The async synthesis/gap scheduler path never checks the cap** — `AnalysisScheduler.advanceClaim` gates on subscription only (:140-169). The sync `runFullPipeline` checks once at entry, with an explicit comment about why not mid-pipeline (PipelineService.java:164, :181-186).
- **Per-run figures:** no constant in code; per-claim actuals come from `AiCallLogRepository.totalCostByClaimId` (repository/AiCallLogRepository.java:19-20) and `PipelineMetrics.totalCostUsd` (PipelineVerifierService.java:233-243, logged at PipelineService.java:200-202). `StrategyDebugController` claims "~2500 tokens saved per decision-tree skip" (:125-129) but that machinery is inactive.
- **Structural $-per-analysis** (N = condition count, A = atom dump size): gap run = N× Claude Opus batch (gap_evidence: ~0.7k system + KB slice + full atom dump in; ≤8k out + thinking) + N× Claude Opus batch (gap_validation: same context + serialized gaps) + N× Gemini (gap_whatif, small input, ≤64k out cap). Synthesis run = 1 Gemini identify (full atom dump) + 1 Claude Opus merger + N× Gemini rate (each with the **full** atom dump again) + 1 Gemini verify. Input tokens scale **O(N×A)** because every per-condition job re-sends every atom; with Opus at $15/1M in / $75/1M out (book rate), the two Claude gap stages dominate. The $4/month cap implies roughly one-to-two full analyses of a mid-sized claim per user per month at logged (2×-inflated) Claude rates.

## 6. STATIC vs DYNAMIC

**Static (everything, essentially):**
- Stage graph is fixed and linear per machine; fan-out width is fixed at one job per condition per stage. No conditional model choice, no budget-aware routing, no per-condition depth control (a 10%-tinnitus condition gets the same Opus gap+validation+whatif treatment as a complex PTSD claim).
- Prompts are compile-time constants; KB injection is a fixed ≤12-sibling slice; thinking budgets and maxTokens are constants per class.
- The only adaptivity that exists: fast-path skips when a stage has nothing to do (GapStateMachine.java:87-91, :171-176, :239-243); the validator can *shrink* the gap list (the one genuinely agentic touch — generator/critic pair); routing precedence allows per-request provider/model overrides (LlmProviderRouter.java:55-70) that nothing in the gap pipeline uses; orphan-recovery self-heals infra failures.
- Dead "strategy" layer: `VasrdDecisionEngine` (deterministic ratings), `EvidencePreComputer` (atom filtering/briefs), `ConditionPromptTemplates` (per-body-system prompts) are referenced **only** by `StrategyDebugController` and themselves — the live `RatingAgent`/`EvidenceGapAnalyzer` do not use them (grep: only StrategyDebugController.java + the three classes). `/api/claim/debug/strategy-info` advertises S1/S3/S4/S13/S17/S20 as "active: true" (StrategyDebugController.java:80-123) — false today.

**Where a dynamic Claude-agent loop would plausibly help:**
- Evidence triage: an agent that reads the condition + triad and *decides* which atoms/KB sections to pull (tool-use over Postgres/masterlist) instead of O(N×A) atom dumps — directly attacks the cost structure.
- Adaptive depth: skip validation/whatif for code-rated or evidence-complete conditions (resurrecting the dead `VasrdDecisionEngine` idea as agent tools); spend Opus-level reasoning only where triad legs are contested.
- Incremental delta analysis: "given these 12 new atoms, which conditions/gaps change?" — impossible in the current full-redo design, natural for an agent with read tools over prior artifacts.
- Self-validating structured output (tool-enforced schemas) replacing fence-stripping + silent-fallback parsing.
- True retry/repair: an agent can re-ask on malformed output; the state machine can only stall.

**Where a dynamic loop would hurt:**
- The batch-economics: gap_evidence/validation ride the 50%-off Batches API precisely because the fan-out is static and embarrassingly parallel; a sequential agent loop on realtime pricing could double-to-quadruple unit cost unless batched tool-parallelism is preserved.
- Determinism & auditability: `LlmJob.request_payload/response_payload` is a complete replayable audit trail per stage; free-form agent trajectories need an equivalent (important for an education-not-legal-advice product).
- The crash-safe, multi-instance-safe DB-queue substrate (SKIP LOCKED submitter, orphan recovery) is genuinely solid and worth keeping under any agent runtime.
- Cost capping is already weak (Section 5); an unbounded agent loop without per-run budget enforcement would make it worse.

## 7. WEAKNESSES (concrete, cited)

1. **Perpetual re-analysis loop (likely live cost bug):** model-change triggers compare `claude-opus-4-7` against stored `gemini-3.1-pro-preview`/`unknown` — never equal → synthesis & gap re-trigger after every completion. AnalysisScheduler.java:192,207 vs SynthesisStateMachine.java:297-303, GapStateMachine.java:273-278, LlmProviderRouter.java:89-95.
2. **Stale fan-out rows never cleaned:** `ClaimPipelineJobRepository.deleteByClaimIdAndStage/deleteByClaimId` (repository:26-34) have zero call sites; readiness checks and parse loops on re-runs consume prior-run rows (`findByClaimIdAndStage`), and `doMergeIfReady`/`doRateIfReady` blindly take `pjobs.get(0)` with no ordering (SynthesisStateMachine.java:121-133, :165-168; GapStateMachine.java:127-147).
3. **Append-only conditions and atoms in the async path:** no `IdentifiedCondition` deletion (only debug IntakeController.java:552) and no `postProcess` dedup (only sync path PipelineService.java:176); extraction re-runs all evidence and re-inserts atoms (ExtractionStateMachine.java:120-141, :196-218) → duplicate atoms/conditions compound across runs.
4. **One FAILED LLM job bricks the claim:** stage gates use `allSucceeded` only; FAILED is non-terminal for the machine — no failure branch, no stage retry, claim stuck with `gapState` set and in-progress flags true forever (GapStateMachine.java:131-132, :193-198, :260-261; `allTerminal` unused, LlmJobService.java:106-109).
5. **Usage cap not enforced where the money is spent:** async synthesis/gap submission path never calls `UsageGuard` — only extraction entry (PipelineService.java:72) and chat (ChatService.java:71); `AnalysisScheduler.advanceClaim` checks subscription only (:140-169). Combined with weakness 1, spend is unbounded per claim.
6. **No structured-output enforcement; silent degradation:** fence-strip + Jackson + fallback-to-empty/defaults everywhere (EvidenceGapAnalyzer.java:160-168; GapValidationAgent.java:211-214 *keeps unvalidated gaps* on parser failure; RatingAgent.java:122-129 silently writes rating 0/confidence 0.3). `LlmJobRequest.tools` support exists but is unused by these agents.
7. **O(conditions × atoms) token waste:** every per-condition gap/validation/rating job embeds the full claim atom dump (GapStateMachine.java:93-98, :134; SynthesisStateMachine.java:184-191; RatingAgent.java:187-193); the built filtering layer (`EvidencePreComputer`, `ConditionPromptTemplates`, `VasrdDecisionEngine`) is dead code only advertised by StrategyDebugController.java:80-129, whose POST endpoints throw 500 via the deprecated stub (StrategyOrchestrator.java:28-32).
8. **Cost accounting wrong for Claude batch:** AiCostService PRICING (AiCostService.java:23-32) charges full Opus rates although batches are 50% off (AnthropicBatchProviderImpl.java:25-26) — user caps consumed ~2× too fast for gap stages; cache-token columns never filled; daily $5/$20 alerts log-only (AiCostService.java:84-92).
9. **Fragile glue between stages:** WhatIf prompt reads `gap.get("impact")` which no upstream schema produces (gaps carry `rating_impact`) → impact column always empty (WhatIfScenarioGenerator.java:72-77 vs EvidenceGapAnalyzer.java:66-80); what-if prompt hard-codes "2024 VA rate tables" (WhatIfScenarioGenerator.java:44) in mid-2026; `markGapAnalysisComplete` model taken from `whatifPjobs.get(0)` arbitrarily (GapStateMachine.java:273-276); scheduler `findAll()` over every claim every 15 s (AnalysisScheduler.java:122-131) won't scale; circular bean deps papered over with `allow-circular-references: true` (application.yml:4-9).
10. **Restart/duplication hazards in the provider layer:** Gemini results live only in an in-memory map (VertexGeminiAsyncProviderImpl.java:31-35, :51) — JVM restart costs up to 30 min orphan-deadline latency and a full re-pay of the call; orphan requeue of an Anthropic SUBMITTED job re-submits a possibly still-running batch (LlmJobPoller.java:113-125 + no cancel on requeue) → duplicate spend; `IdentifiedCondition` lacks `updatedAt`, so user edits can never re-trigger gap analysis (AnalysisScheduler.java:210-213).
